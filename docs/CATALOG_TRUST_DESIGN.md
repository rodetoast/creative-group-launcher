# 카탈로그 신뢰 모델과 후속 보안 설계 검토

2026-11-03. **설계 검토이며 서명/TLS 구현 완료 문서가 아니다. 실제 회사 프로그램의 일반 팀원 배포는 계속 보류한다. 제한된 LAN 시험은 승인된 더미만 사용한다.** 이번 수정에서 암호화 라이브러리·키·인증서·네트워크 공개 설정을 추가하지 않았다.

## 현재 신뢰 경계

[HttpProvider](<../southpaw_tools/providers.py#L42>)는 사설/loopback IP의 HTTP에 접속한다. LAN Bearer 공유 토큰은 다운로드 접근을 제한하지만 서버를 인증하지 않으며 평문 네트워크에서 노출/재사용될 수 있다. 클라이언트 settings.json도 평문 저장이다. IP가 사설이라는 사실은 회사 서버의 신원 증명이 아니다.

[카탈로그 검증](<../southpaw_tools/catalog.py#L37>)은 스키마/경로/해시 형식을 검사한다. [관리자 게시](<../southpaw_tools/admin.py#L16>)는 로컬 승인 CLI와 원자적 게시를 제공하지만 --approve/published=true가 전자서명은 아니다. 서버 파일을 쓰는 OS 계정이 현재 실질적인 게시 권한자다. 일반 HTTP 사용자의 업로드 endpoint는 없다.

ZIP·EXE SHA-256은 받은 메타데이터와 파일의 일치만 보장한다. 공격자가 카탈로그와 ZIP을 함께 바꾸고 새 release_id를 주면 현재 엔진은 이를 진짜 게시물과 구별하지 못한다. 동일 ID/다른 해시 거부는 부분적인 불변성 검사이며 게시자 인증·최초 신뢰·재전송 방어가 아니다. 이 위험은 안정성 수정 후에도 남는다.

## 구현 가능성 및 제안

다음은 후속 제안이며 이번 작업에서 활성화하지 않았다.

1. **초기 신뢰:** 배포한 런처에 신뢰 루트 공개키와 key_id를 포함한다. 네트워크에서 처음 받은 키를 무조건 신뢰하지 않는다. 런처 자체 배포물의 진위/코드 서명과 최초 배포 경로도 보호해야 공개키 고정이 의미가 있다.
2. **서명 형식:** 검토 후보는 Ed25519. 서명 입력의 정확한 UTF-8 bytes/정규화 방식, envelope schema, 중복 JSON 키 거부, 크기 제한을 명세한다. 게시 앱 ID, version, release_id, ZIP/EXE 해시와 크기, 실행/cwd/필수/보존 경로, 배포 채널, 만료, 단조 증가 sequence를 모두 인증 범위에 넣는다. 서명 확인 후에만 메타데이터/캐시를 채택하고 설치를 허용한다.
3. **키 보관:** 서명용 개인키는 관리자 전용 비공개 위치/서명 장치에 보관한다. 소스 저장소, 팀원 런처, distribution 폴더, HTTP 응답, 로그, 테스트 fixture에 넣지 않는다. 서버에는 서명된 결과물만 복사하는 오프라인 게시 방식이 가능하다.
4. **실패 정책:** 누락/알 수 없는 키/서명 실패/만료/과거 sequence면 신규 다운로드·업데이트를 차단하고 unsigned로 자동 후퇴하지 않는다. 마지막 정상 캐시·설치 상태를 보존한다. 정상 설치된 로컬 프로그램 실행에는 새 서버 조회나 카탈로그 만료를 필수 조건으로 넣지 않는다.
5. **키 회전/재전송:** 키 교체·폐기·유출 복구·루트 업데이트와 이전 메타데이터 재전송 방어가 필요하다. 고정 공개키 한 개와 단순 서명만으로 이 전체 문제를 해결했다고 주장하지 않는다. 운영자가 승인한 다운그레이드는 별도 승인 기록으로 다룬다.
6. **서버 진위/기밀성:** 회사 관리 CA/인증서를 통한 HTTPS 및 인증서 수명·교체 절차를 검토한다. IP 직접 연결을 유지하면 인증서의 IP SAN 또는 검증된 내부 DNS 이름이 필요하다. 인증서 검증 끄기는 대안이 아니다. 서명은 게시자/내용의 신뢰, TLS는 연결 상대/전송 보호를 담당하며 서로 대체하지 않는다. 사용자별 인증·토큰 회전/보관 강화는 별도 검토한다.

Ed25519 서명/검증은 검증된 라이브러리의 API로 구현 가능하지만 현재 의존성인 Python/PySide6만으로 구현됐다고 볼 수 없다. 라이브러리와 Windows wheel/라이선스/패키징/암호 백엔드를 검토하고 버전을 고정해야 한다. 자체 암호 구현은 제안하지 않는다. API 근거: [cryptography Ed25519 공식 문서](https://cryptography.io/en/latest/hazmat/primitives/asymmetric/ed25519/).

키 회전·역할 분리·만료·재전송 방어까지 필요하면 기존 프레임워크 채택을 비교 검토한다. TUF는 신뢰 루트와 서명된 업데이트 메타데이터 검증 절차를 정의하므로 참고할 수 있다. 이 프로젝트가 현재 TUF를 구현하거나 준수한다는 뜻은 아니다. 근거: [The Update Framework specification](https://theupdateframework.github.io/specification/latest/).

## 후속 검증 기준

- 카탈로그만 변조, ZIP과 함께 변조, 잘못된 키, signature 바이트 변조, metadata 혼합, 만료·sequence 후퇴는 모두 신규 설치 차단.
- 키 교체 전/후 client, 손상 캐시, 잘못된 시계, 게시 중 서버 장애에서도 정상 이전 설치와 로컬 실행 유지.
- 개인키가 client/공개 폴더/로그에 없는지 검증. 서버 파일 쓰기 권한과 다운로드 권한을 OS/운영 절차로 분리.
- 보안 설계와 별도 구현·재감사 전 실제 회사 프로그램 일반 배포를 진행하지 않는다. LAN/인터넷/방화벽 설정은 이번 수정 범위에서 변경하지 않았다.
