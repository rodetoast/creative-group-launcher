# Southpaw 도구 런처 — 장애 대응 및 제한 사내 파일럿 운영 인계

기준일: 2026-11-13. 개발 PC DESKTOP-1MK6D95 / 검증 PC SPENT03. 이 문서는 지원 절차와 파일럿 판단을 확정하며, 설치·복구·게시를 실행하거나 직원 배포를 승인하는 문서가 아니다.

**운영 판단: 담당자 동행의 소수·분리된 파일럿은 조건부 진행 가능. 무지원 전체 배포는 보류한다.** 아래 시작 준비4가지를 정하면 추가 원인 조사나 전체 회귀 반복을 파일럿 시작의 선행조건으로 두지 않는다.

## A. 직원·담당자용 장애 대응 안내서

### 직원에게 전달할 최초 안내

> 런처가 열리지 않거나 오류가 나오면 반복 실행하지 말고 담당자에게 알려 주세요. 오류 화면과 발생 시각, 마지막 작업(최초 실행/업데이트 직후/종료 후 재실행)을 남겨 주세요. 런처 폴더와 회사 프로그램·설정·작업 파일은 그대로 두세요. 관리자 실행, 파일 삭제, 재설치, 보안 설정 변경은 직접 하지 마세요.
>
> 담당자 안내 전에는 버전 폴더의 EXE를 직접 실행하거나 현재 버전을 바꾸지 마세요. 급한 업무는 미리 지정된 기존 업무 수단으로 전환하세요. 런처 저장소의 EXE 직접 실행을 장애 복구 방법으로 제공하지 않습니다.

직원이 보낼 내용은 ①발생 시각 ②오류 문구/화면 ③마지막 작업 ④지금도 런처 창이 보이는지다. 토큰·nonce·개인 작업 파일·폴더 전체는 채팅에 보내지 않는다. 오류창에 사용자 정보가 보이면 공유 범위를 담당자와 확인한다.

GUI는 열리고 GitHub 연결만 실패한 경우는 Bootstrap 시작 장애와 구분한다. 기존 설치 앱의 정상적인 로컬 실행 기능은 유지되는 설계다. 이 경우에도 파일을 다시 설치하거나 서명 검증을 우회하지 않는다.

### 담당자가 먼저 확인할 것

설치대장에서 **I=설치 폴더, H=I\launcher-home, D=앱·사용자 데이터 폴더**를 확인한다. 기본 D는 `%LOCALAPPDATA%\SouthpawGames\ToolsLauncher`지만 파일럿·시험에서 별도로 지정했을 수 있다. 기본값을 추측해 다른 자료를 검사하거나 새 데이터 경로로 실행하지 않는다. 기존 바로가기 인자, H\layout.json의 user_data_root, I\setup-state.json의 data_root를 읽기 전용으로 대조한다.

1. 실제 시작 파일이 I\CGLBootstrap.exe인지 확인하고 지원 대장의 승인 SHA256과 대조한다. GUI 버전 폴더의 CreativeGroupLauncher.exe를 Bootstrap 대신 실행하지 않는다.
2. 오류 직전/직후 로그와 현재 상태를 읽는다. 새로운 실행·복구 호출로 상태를 바꾸기 전에 증거를 남긴다.
3. 해당 설치 경로의 Bootstrap/GUI가 실행 중인지 읽기 전용으로 확인한다. 이름만 같은 다른 설치나 과거 PID를 대상으로 종료하지 않는다. 조회 실패/접근 거부/모듈 없음은 '실행 중 아님'이 아니다.
4. 외부 통신 실패, 서명/해시 실패, 파일 접근 오류, 실행 중 보호, 복구 필요를 분류한다. 'WinError5'라는 번호만으로 파일 잠금·백신·PID 재사용을 원인으로 단정하지 않는다.

담당자의 기존 승인된 Python과 진단 스크립트가 있을 때만 다음 **읽기 전용 명령**을 사용할 수 있다. 직원 PC에 Python이나 패키지를 새로 설치하도록 요구하지 않는다. `<...>`는 실제 기록된 절대경로로 대체한다.

```powershell
& '<기존 Python.exe>' -B '<검증된 launcher_diagnostics.py>' --data-dir '<D>' --launcher-home '<H>' --summary
& '<기존 Python.exe>' -B '<검증된 launcher_diagnostics.py>' --data-dir '<D>' --launcher-home '<H>' --json
```

스크립트는 기존 `tools/launcher_diagnostics.py`다. 파일/상태/로그/등록을 조회하며 설치·복구·네트워크 요청을 하지 않는다. 파일 JSON 출력이 필요하면 기존 자료와 겹치지 않는 새 Evidence 폴더에 담당자가 저장한다. 의존성 없는 단독 실행은 기본 상태만 보여 줄 수 있다. signature 검증기 없음, identity_module_unavailable, query_failed, inaccessible_process_count 또는 읽기 오류가 있으면 해당 항목을 미확인으로 기록한다. 빈 processes 배열만 보고 재설치해도 안전하다고 판정하지 않는다.

CLI 요약은 정밀 operation을 전부 보여 주지 않는다. 원래 Bootstrap 오류 JSON의 diagnostics를 함께 읽는다. 로그가 없으면 '로그 없음/기록 실패'로 남기며 다시 실행해 로그를 만들도록 유도하지 않는다.

| 위치 | 확인 사항 |
|---|---|

| H\transactions\*.json | committed/rolled_back/미완료 상태. 오류·미완료면 원본 보존. committed 하나만 보고 모든 거래가 정상이라고 가정하지 않음 |

담당자는 원래 설치/데이터 위치와 참조한 파일 목록·시각을 기록한다. 상태가 멈춘 것을 확인할 수 있을 때 I(특히 H와 소유권 표식), D 및 실제 외부 작업 경로의 필요한 범위를 **원본을 이동하지 않는 사본**으로 보호한다. 살아 있는 작업자/파일 잠금 때문에 일관된 사본을 만들 수 없으면 그 사실을 남기고 변경 작업을 중단한다. 로그 몇 개만 복사하고 전체 데이터 백업이 끝났다고 보고하지 않는다.

### 즉시 변경을 중단하는 조건

- Bootstrap/업데이트 작업자가 아직 실행 중이거나 상태를 확인할 수 없음.
- 서명·ZIP/실제 파일 해시 불일치, current/receipt 손상, 미완료·복구 필요 상태.
- 같은 설치의 파일 접근 거부, 로그 저장까지 실패, 기존 자료 보존 여부 불명.
- Setup이 변경된 관리 파일·다른 소유자·기존 데이터 경로 충돌·실행 중 상태를 이유로 거부함.
- 보안 정책/UAC·관리자 권한·ACL 변경을 해야 진행할 수 있다고 보임.
- 회사 앱/작업 파일 해시가 예상 없이 변했거나 소실된 정황.

이때 반복 클릭, taskkill/강제 종료, probe-owner/lock/journal/current 삭제, launcher-home 초기화, 오래된 포인터 덮어쓰기, 다른 경로로 몰래 재설치, SAC·보안 제품 우회를 하지 않는다. 실제 파일 선택·복구 상태를 수동 편집하는 지원 명령은 제공하지 않는다.

### Setup 재설치: 가능한 범위와 한계

**검증된 자동 Bootstrap 장애 복구 방법 없음. 기존 자료 보존 후 담당자 지원 필요.** 특히 B14 recovering→failed/WinError5가 Setup 재설치로 해결된 시험은 없다.

| 상황 | 담당자 판단 |
|---|---|
| 정상 소유권·같은 위치/데이터·일치하는 관리 파일·실행 종료 확인 | 동일한 검증 Setup의 재설치 경로는 기존 Setup 실기동/회귀 근거가 있음. 보존 사본 후 담당자 통제하에 적용 가능하지만 이번 문서 작성에서 실행하지 않음 |
| 승인 관리 파일 일부가 없어졌고, 남은 파일/표식은 해당 Setup과 일치 | 코드상 누락 관리 파일의 재배치가 가능한 범위. 실제 장애 해결은 미검증이므로 사용자 자가 복구로 약속하지 말고 담당자 사안별 판단 |
| 관리 파일 내용/해시가 Setup manifest와 다름 | 기존 guard가 덮어쓰기를 거부함. 재설치로 강제 수리하는 제품이 아님. 파일을 지워 검사를 우회하지 않음 |
| launcher-home의 owner/current/receipt/거래 접근 실패 | 재설치는 H를 보존하므로 같은 장애가 남을 수 있음. 초기화/포인터 수정/자동 해결을 안내하지 않음 |
| 정상 제거 뒤 H와 데이터가 남음 | 의도된 보존 정책. 기존 Setup 시험에서 정상 제거/재설치 근거가 있고, BD13에서는 제거 및 자료 보존이 관측됨. **BD13 제거 후 재설치로 Bootstrap 장애까지 해결됐다는 결과는 없음** |
| 다른 Setup·다른 Bootstrap으로 교체하려는 경우 | 서로 다른 manifest는 기존 파일 변경으로 거부될 수 있음. 같은0.1.4.0 표기만으로 호환 판정하지 않음. 검증된 교체 패키지·절차가 없으면 상위 지원 |

재설치를 선택할 때 담당자가 확인할 조건은 동일 승인 자산의 **파일 해시**, 채널/공개키/seed, 원래 I/D, 설치 표식과 관리 파일, 종료된 프로세스/잠금, 보존 사본이다. Setup 버전 문자열만 대조해서는 안 된다. Setup이 실패하면 결과·중간 상태를 남기고 같은 명령을 반복하지 않는다. 성공 뒤에도 실제 정상 시작·종료와 앱 상태/사용자 데이터 보존을 확인해야 지원 완료다.

제거는 런처 초기화 기능이 아니다. 원래 소유한 I\Uninstall.exe가 있고 소유권/실행 중 보호를 통과하는 경우의 공식 제거만 사용한다. 설치된 앱 목록에 안 보일 때도 **담당자가 경로와 소유권을 확인한 해당 Uninstall.exe**가 제거 경로다. 직원에게 폴더 삭제를 대신 안내하지 않는다. 기존 데이터와 H가 남는 것을 오류로 보고 지우지 않는다.

### 담당자에게 전달할 최소 자료와 지원 종료 기준

한 건의 기록에 다음만 모은다.

- 실제 PC/사용자 역할, 발생 시각·시간대, 마지막 동작, 오류 문구 또는 검토한 화면1개.
- 승인 Setup/Bootstrap의 파일명·SHA256, 현재 GUI version/release_id, I/H/D가 어느 설치인지 식별 가능한 가린 경로.
- 해당 실행의 bootstrap-runs/errors, 읽기 전용 진단 요약. current/거래/app 상태는 필요한 요약과 해시 전후 비교.
- 남아 있는 프로세스의 확인 상태와 읽기 오류, 데이터 보존 확인/미확인, 담당자가 수행한 조치와 결과.

전체 sessions, 원문 stdout/stderr, nonce/토큰/키, 사용자 작업 파일, 프로필 전체를 자동 첨부하지 않는다. 원본은 로컬 비공개로 보존하고 공유 사본은 검토한다. 기존 Private 증거 저장소 도구를 사용할 수 있지만 게시 승인은 해당 지원 업무 범위를 따른다. 공개 시험 Release에 장애 원본을 올리지 않는다.

담당자가 소유권/정상 종료/해시/데이터 보존을 확인할 수 없거나, 한 번의 승인된 조치 뒤 같은 장애가 남거나, 복구 상태/정책 변경이 필요해 보이면 **지원 중단→개발 담당자 또는 사내 IT 상위 지원**으로 이관한다. 근거 없이 직원에게 원인 조사 명령을 계속 실행시키지 않는다. 자료 보존 여부와 대체 업무 경로를 인계하고 장애를 열린 상태로 기록한다. 데이터 변경·소실, 서명 불일치, 여러 참여자의 같은 시작 장애는 새 파일럿 설치/업데이트를 즉시 보류할 기준이다.

## B. 제한된 사내 파일럿 준비 상태 판정

### 판정과 최소 시작 준비4가지

**기술 판정: 조건부 GO — 담당자 동행의 소수 파일럿. 전체 배포: 보류.** SPENT03의 이번 성공이 B14 원인 해결을 뜻하지는 않지만, 검증되지 않은 원인 조사를 계속하는 대신 장애 시 변경 중단·자료 보존·담당자 이관을 운영 절차로 수용할 수 있다.

추가 원인 조사/재빌드/전체 회귀 반복 없이 파일럿을 열기 전에 아래4가지만 운영 기록에 확정한다.

1. **대상과 담당자:** 예를 들어 자원자2~3명, 지원 담당자·대체 담당자·연락 수단·지원 가능한 시간을 지정한다. 구체적인 성명/연락처는 이 문서가 임의로 만들지 않는다.
2. **단일 지원 기준:** 사용할 검증된 Setup/Bootstrap/채널/공개키/해시와 원래 설치·데이터 경로를 대장에 고정한다. 시험 후보를 운영 승인본으로 부르지 않는다. 기존 직원 설치 위의 마이그레이션·공용 데이터 병합은 파일럿에서 제외한다. 기존 시험 등록이 있는 PC는 원래 경로를 무시해 덮어쓰지 않는다.
3. **자료와 업무 연속성:** 신규·분리 데이터부터 사용하고, 유일한 원본 작업 파일을 시험 자료로 삼지 않는다. 장애 시 기존에 승인된 업무 수단으로 전환할 수 있는지 확인한다. 런처만이 유일한 업무 진입점인 사용자는 첫 파일럿 대상에서 제외한다.
4. **기록과 멈춤:** 설치 기준 상태 및 실제 사용 중 시작·업데이트·종료/재실행·데이터 보존 결과를 간단히 기록한다. A의 중단·이관 기준을 참여자에게 전달한다. 성공 횟수만 정해 오류를 묻거나 자동으로 참여 인원을 늘리지 않는다.

위 운영 지정은 현재 대화에서 확인되지 않았다. 이미 정해진 항목은 기존 기록을 재사용하면 되며 중간 승인을 다시 요청할 필요가 없다. 이 문서 자체는 새 PC의 설치/직원 배포를 실행하지 않는다. B14 원인 미확정만을 이유로 위 범위의 파일럿에 ProcMon·추가 합성 시험·319개 재실행을 요구하지 않는다.

### 남은 문제 분류

| 분류 | 문제·판단 | 현재 운영 조치 |
|---|---|---|
| 파일럿 시작을 막는 문제 | 승인할 단일 패키지/채널/해시·I/D, 지원 담당자, 자료 보존/대체 업무 수단 미지정 | 위4가지 기록 후에만 시작. 테스트/운영 파일 혼용이나 기존 데이터 덮어쓰기로 시작하지 않음 |
| 대응 절차가 있으면 수용 | 과거 B14 Bootstrap WinError5 원인 미확정, 검증된 자동 장애 복구 없음 | 진단 포함 후보·증거 보존·무조건 재시도 금지·담당자 이관으로 소수 파일럿에서 수용. 새 PC 성공을 근본 해결로 표시하지 않음 |
| 대응 절차가 있으면 수용 | GitHub/네트워크·서명 검증 실패에 따른 업데이트 보류 | 기존 설치본을 유지하고 안내/지원. 서명 실패를 인터넷 오류로 혼동하거나 우회하지 않음 |
| 정식 전체 배포 이전 개선 | 원인 미확정 파일 접근 장애 발생 시 담당자가 처리할 검증된 복구/Bootstrap 교체 경로가 부족함 | 전체 배포 전 데이터 보존과 실패 시 중단까지 포함한 지원 경로를 검증해야 함. 지금 자동 복구 명령을 만들어 내지 않음 |

업무 중 데이터 소실/서명 우회/출처 불명 패키지가 새로 확인되면 위의 '수용' 판정을 계속 적용하지 않는다. 해당 참여자 및 새 설치/업데이트를 보류하고 담당자에게 이관한다.

### 판단에 재사용한 실제 근거와 한계

- SPENT03 결과는 사용자의 최신 완료 보고를 기준으로 한다: GUI0.1.3→0.1.4, 동일 Bootstrap 재실행, 정상 종료·자료 보존, BD13 제거 후 관리형 데이터·합성 파일 보존. 이번 작업에서 원본 증거를 다시 다운로드하거나 같은 시험을 실행하지 않았다.
- 제품 소스 전체319개 통과 및 정밀 진단 구현을 재사용한다. 테스트 통과가 간헐적 WinError5 근본 원인 해결을 증명하지 않는다.
- B14는 업데이트·새 GUI 정상 종료 뒤 재실행 recovering→failed/WinError5. 정확한 API·파일 원인은 여전히 미확정. PID 재사용·보안 제품 원인으로 단정하지 않는다.
- 정상 Setup 재설치/제거/데이터 보존 근거는 기존 Setup 개발 실기동 기록과 tests/test_setup_support.py를 재사용한다. BD13 제거 성공과 **장애 상태에서의 재설치 복구 성공**을 혼동하지 않는다.

지원용 검증 후보 식별 참고(직원 운영 배포 승인표가 아님): `bootstrap-diagnostics-spent03-20261113`, 시험 채널 toast-source/creative-group-trial-releases, 기존0.1.3 seed/순번9→기존 순번10/0.1.4.
